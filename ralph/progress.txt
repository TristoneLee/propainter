## Codebase Patterns
- Runtime A/B switches: gate via env var (e.g., `_FLEX_ATTN = os.environ.get('PROPAINTER_FLEX_ATTN', '0') == '1'`) at module top in `model/modules/sparse_transformer.py`. CLI flags in `inference_propainter.py` / `benchmark_propainter.py` must pre-parse `sys.argv` BEFORE the `from model.modules...` imports because module-level constants are bound at import time.
- Both `inference_propainter.py` and `benchmark_propainter.py` import `model.modules.flow_comp_raft` at the top, which transitively imports the transformer module — so any env var the transformer reads at import must be set before line ~14 in those files.
- argparse for `inference_propainter.py` lives inside `if __name__ == '__main__':` block (~line 209); for `benchmark_propainter.py` it lives in `def main():` (~line 462).
- Optional torch features (e.g., `torch.nn.attention.flex_attention`) should be imported inside a `try/except ImportError` and the module-level enable flag flipped to False with a `warnings.warn` if the user requested the feature but the runtime can't supply it. Set the symbols (`flex_attention`, `create_block_mask`) to `None` in the except branch so downstream `if _FLEX_ATTN:` branches can still type-check / load.
- Original `SparseWindowAttention` unmasked branch does PER-FRAME attention: `win_q_s @ win_k_s.transpose(-2,-1)` is a 5D batched matmul broadcasting over (n_unmask, n_head, t) with each frame's softmax over W keys. The masked branch is cross-temporal (Q_LEN=t*W, KV softmax over T_sel*(W+roll+pool)). Any rewrite must mirror this asymmetry to preserve numerical equivalence — folding (b, n_win, t) into the batch dim for the unmasked flex_attention call is the natural way to do this with `_row_select_block_mask`.
- `T_ind` is generated CPU-side by `torch.arange` in `TemporalSparseTransformerBlock.forward`; consumers that use `index_select` (which requires same-device indices) need an explicit `.to(win_k.device)` — legacy advanced indexing handled this implicitly.
- 720p post-encoder shapes: `fold_x_size = (180, 320)` (encoder strides 4×). SoftSplit kernel (7,7), stride (3,3), padding (3,3) yields `f_h = int((180+6-6-1)/3+1) = 60`, `f_w = int((320+6-6-1)/3+1) = 107`. The transformer-block input is `[B, T, 60, 107, 512]`; the 60x108 grid that appears in profiles is the post-pad grid inside `SparseWindowAttention.forward` (pad_r=1 to align to window_size=(5,9)).
- Toggling `_FLEX_ATTN` at runtime: tests can flip `model.modules.sparse_transformer._FLEX_ATTN = True/False` without re-importing because the `if _FLEX_ATTN:` check inside `SparseWindowAttention.forward` reads the module-global on every call. Useful for A/B equivalence tests in a single process.
- fp16 numerical equivalence between the legacy SDPA loop and the FlexAttention path is tight at the SparseWindowAttention layer (~3.9e-3 max_abs_diff with x_scale=0.1) but compounds through the 8-layer `TemporalSparseTransformerBlock` to ~0.3 abs diff. fp32 is bit-exact (max_abs_diff=0) at every level, so end-to-end correctness is verified by fp32 bit-exactness; the fp16 layer-level bound is the tightest meaningful per-call check.
- Eager flex_attention (no torch.compile wrapper) materializes the full per-row scores matrix internally; on the per-frame unmasked branch this is a `(BN*t, n_head, W, W)` tensor that grows linearly with chunk length t. On a 32GB GPU this OOMs around T~21 (i.e. full 127-frame 720p video). For end-to-end smoke tests in eager mode keep the inference chunk small (`--frames 30` works); compile mode (US-007/US-008) is expected to remove the materialization.
- `inference_propainter.py` has two foot-guns that need to be aware of when running it programmatically: (1) `torchvision.io.read_video` is gone in torchvision >= 0.26 — fall back to `imageio.v3.imread` (already imported); (2) `--frames N` only truncates the frames list, NOT the parallel mask list, so `flow_masks/masks_dilated[:frames_len]` after `read_mask(...)` is required to keep RAFT/flow-completion tensor shapes aligned. Both fixes landed in this branch.
- NVTX instrumentation pattern in `model/modules/sparse_transformer.py`: `_NVTX = os.environ.get('PROPAINTER_NVTX', '0') == '1'`, with `_NvtxRange` context manager and `_rf(tag)` helper that returns the NVTX range when `_NVTX` is set, a `torch.profiler.record_function(tag)` when `_PROFILE` is True (kept False; reserved for python-side profiling), and `contextlib.nullcontext()` otherwise. Keep production runs paying zero overhead by NEVER setting `_NVTX` outside the nsys script. Tag names used by analyzers: `tst/block`, `tst/norm1|norm2`, `tst/attn/{qkv_proj,win_partition_qkv,roll_expand,pool_kv,mask_prep,sdpa_loop,unshuffle_proj}`, `tst/ffn/{fc1,fold_unfold,fc2}`. The FlexAttention path keeps the same `tst/attn/sdpa_loop` tag as the legacy path so per-call wall comparisons work apples-to-apples.
- nsys capture-iter fence in `inference_propainter.py`: set `PROPAINTER_NSYS_CAPTURE_ITER=N` (default -1 = disabled) to trigger `cudaProfilerStart`/`cudaProfilerStop` around iteration N of the feat_prop+transformer loop. Pair with `nsys profile --capture-range=cudaProfilerApi --capture-range-end=stop`. Iter 1 is the recommended choice for eager mode (past first-touch) and iter 5+ for compile mode (past dynamo recompiles).
- nsys driver script `scripts/experiments/nsys_transformer.sh` is parameterized: setting `PROPAINTER_FLEX_ATTN=1` rewrites the report names to `fp16-eager-flex` / `fp16-compile-flex` and forwards `--use-flex-attn` to inference. Use `--eager-only` to skip the slow compile run while iterating on the eager flex path. The set-euo-pipefail will exit on a non-zero python (e.g. OOM) — regenerate stats manually with `nsys stats --force-export=true ...rep` if the python process crashed *after* the capture range closed.
- Eager `flex_attention` (no torch.compile wrapper) dispatches to `_higher_order_ops.flex_attention.sdpa_dense -> math_attention`, which materializes the full `(B, H, Q, KV)` scores in fp32 working precision. On 720p with `subvideo_length=100 neighbor_length=10` this single allocation is ~6.93 GiB and OOMs the 32GB GPU after the first transformer block. The fp32 simt_sgemm/magma_sgemmEx kernels visible under `tst/attn/sdpa_loop` in the new path are *internal to math_attention*, not introduced by ProPainter user code (US-010 should investigate but cannot fix downstream of torch).
- `create_block_mask` (and any data-dependent BlockMask construction) **must NOT run inside a torch.compile region** on Blackwell (CC 12.0). When traced into the Dynamo graph it emits an inductor-codegen pair (`triton_poi_fused_clone_permute_view_*` and `triton_per_fused__to_copy_bitwise_and_eq_gt_lt_sort_sum_*`) whose runtime autotune crashes with `cudaErrorIllegalAddress`. The crash is reproducible across cache wipes and is not present when compiling the legacy SDPA path on the same GPU. Pattern to use in flex_attention sites that are inside a `torch.compile`'d subtree: branch on `torch.compiler.is_compiling()` and drop `block_mask=` under compile, relying on a downstream `torch.where`/index merge to discard skipped rows. The eager branch keeps `_row_select_block_mask` for its perf benefit.
- `torch.compile(mode='default')` over `model.encoder + model.transformers + model.decoder` on this codebase is graph-break free under the FlexAttention path: at 720p fp16 30 frames, `TORCH_LOGS=graph_breaks` produces zero `[__graph_breaks]` lines. First-iter compile is ~22s, second-iter recompile (different T) is ~28s; subsequent iterations drop to ~1s wall. Two specializations are compiled because T (= local frames + ref frames) varies between the first iteration (no overlap) and later iterations.
- `compare_outputs.py` accepts `--compile-mode <mode>` (and `--compile-fullgraph`) which forwards `--compile --compile-mode <mode>` to the FLEX run only — the legacy run stays eager so PSNR validates compiled-flex against eager-legacy. Pattern for future stories that need a "compile-on, eager-baseline" PSNR check.
- Under `torch.compile --compile-mode max-autotune-no-cudagraphs` on Blackwell + PyTorch 2.11, `flex_attention` lands on a fused `triton_tem_fused_flex_attention_0` kernel that does NOT materialize the scores matrix (no OOM at 720p full video) and the kernel breakdown for `tst/attn/sdpa_loop` has zero `nonzero`/`simt_sgemm`/`magma_sgemmEx`/`index_put` calls — the fp32 leak that motivated US-010 turns out to be an artifact of the eager `math_attention` fallback, not user code. Per-call wall: `tst/block` 38.05 ms (compile-flex) vs 36.97 ms (eager-legacy) — small +2.9 % regression from `index_select(T_ind)` + final `torch.where` merge that the rewrite introduces.

Choose `PROPAINTER_NSYS_CAPTURE_ITER=5` for stable post-autotune measurement (iter ≤ 2 still includes compile work in-loop).
- `nsys_transformer.sh` now has both `--eager-only` and `--compile-only` script-side flags. `--compile-only` skips the eager run, useful when (a) the eager FlexAttention run OOMs after the captured iter and pollutes stderr, or (b) only the compile profile is needed. Mutually exclusive with `--eager-only`; the script exits 2 if both are set.
- `torch.compile(fullgraph=True)` is incompatible with `_NvtxRange` inside the compiled subtree: `torch.cuda.nvtx.range_push` returns `int` (non-Tensor), Dynamo classifies the call as a side-effecting Python op, and under `fullgraph=True` aborts trace with `torch._dynamo.exc.Unsupported: torch.* op returned non-Tensor`. Under `fullgraph=False` (default) the same call only causes a graph break (US-008's data path). Practical workaround for nsys captures under fullgraph: run with `PROPAINTER_NVTX=0` so only the outer `capture/iter{N}` range from `inference_propainter.py` fires (it is outside the compiled subtree); per-tag `tst/*` walls are unavailable but the iter-total wall is.
- Fullgraph compile on this codebase needs no source change beyond what landed for US-007 (the `is_compiling()` BlockMask gate). End-to-end direct run on 30 frames at 720p fp16 takes 33.46 s wall (8 iters; iter 1 ~5.2 s compile, iter 2 ~5.7 s recompile, iters 3-8 ~1 s/iter). PSNR vs eager-legacy mean 43.83 dB / worst 42.00 dB @ frame 15. Under fullgraph, inductor fuses `index_select + arange + ones + sort + sum + flex_attention` into a single fused triton kernel (`triton_tem_fused__to_copy_arange_cat_clone_flex_attention_index_index_select_ones_permute_repeat_slice_sort_sum_transpose_unsqueeze_view_zeros_*`) — bigger fused regions than US-008's max-autotune-no-cudagraphs setting.
- The cheap way to compare iter-wall across compile modes when NVTX inside compile is unavailable: use the `capture/iter{N}` NVTX range from inference_propainter.py (always emitted regardless of PROPAINTER_NVTX). It captures encoder + transformers + decoder + flow + propagation per iter. Subtract a known non-tst baseline from a sibling capture (US-008) to estimate tst-region wall under fullgraph.
- The fp32 simt_sgemm / magma_sgemmEx / softmax_warp_forward<float,float,float> kernels visible under `tst/attn/sdpa_loop` in eager mode (BOTH legacy and flex paths) are NOT introduced by ProPainter user code. Code search of `model/modules/sparse_transformer.py` returns 0 hits for `.float()` / `dtype=torch.float32` / `FloatTensor`; the few default-fp32 constructors (`torch.ones` for `valid_ind_rolled`, `torch.arange` for `T_ind`) feed `.nonzero()` -> int64 index buffers and never enter SDPA math; `tensor_fp16 * python_float` (the `(1.0 / math.sqrt(...))` scale) keeps fp16 per PyTorch weak-scalar promotion (standalone reproducer returns `torch.float16` end-to-end and dispatches to `cutlass_75_wmma_tensorop_f16_*`). The fp32 leak originates downstream: (a) torch's batched-matmul backend selecting a magma fp32 fallback for the unmasked branch's 5D shape, and (b) `_higher_order_ops/flex_attention.math_attention` upcasting scores to `working_precision=fp32` default. Both removed by `torch.compile` (US-008/US-009 capture CSVs grep 0 for simt_sgemm/magma_sgemm/softmax_warp_forward<float,float,float>). US-010 dismisses per PRD bullet 5 (no user-code fix possible).
- `pool_kv` does NOT fuse under `torch.compile`. The kernel list under `tst/attn/pool_kv` is IDENTICAL across eager-legacy / compile-legacy / compile-flex (all max-autotune-no-cudagraphs): 8 direct_copy_kernel + 512 `convolve_common_engine_float_NHWC<__half, ..., 5, 5, 3, 3>` (depthwise pool conv) + 2 cutlass_80_tensorop_f16_s16816gemm_relu + 1 CUDAFunctor_add per transformer block. The depthwise pool conv dispatches through cuDNN's NHWC engine rather than a triton-fusable op, so inductor leaves it untouched. Per-call NVTX wall does drop 5.113 ms → 3.877 ms (-24 %) eager-legacy → compile-flex, but this is launch-latency hiding (host stalls adjacent to the fused flex_attention kernels), not fusion — compile-flex's per-block kernel-sum GPU time is actually slightly higher (+1.58 ms / +16 %). When comparing eager-flex (US-006) directly to compile-flex (US-008), the eager-flex pool_kv NVTX shows only 1 instance at 481 ms because the math_attention fp32 fallback OOM'd partway through; that 1-instance number is OOM-distorted, not a clean baseline. The meaningful baseline for pool_kv comparisons is fp16-eager (legacy SDPA), not fp16-eager-flex.

- **Learnings for future iterations:**
  - When PRD acceptance bullets list a numerical assertion ("kernel X must not appear") AND a dismissal escape hatch ("if the leak is in torch, document and dismiss"), the dismissal applies when user-code search is empty. Don't chase a "fix" through torch internals; document and pivot to the deployment configuration that doesn't have the issue.
  - The standalone reproducer pattern (Python script with `torch.profiler.profile` over the suspect math, no model load) is the cheap way to test a fp32-leak hypothesis without a 30 s model build. If the standalone gives fp16, the leak is shape/stride-driven by the surrounding model context, not by the user-code expression itself.
  - Kernel names with `<float, float, float>` template params are reliable evidence of fp32 work at that op; `<c10::Half, ...>` is fp16. The first two-three template params of pytorch elementwise/softmax kernels are typically `<input_t, accscalar_t, output_t>`.
  - PyTorch weak-scalar promotion: `tensor_fp16 * python_float` keeps fp16 (verified). This is unintuitive vs C type-promotion rules but is the documented PyTorch behavior since 1.5.

This applies to future stories that want to validate "did this op get faster under compile" — use eager-legacy as the baseline, not eager-flex.

## 2026-06-15 - AOTInductor encoder/decoder (branch perf/compile-encoder-decoder)
- Investigated "compile-with-graph / operator fusion" for more 720p80 speedup (14.05s vs original 30.90s baseline).
- Fresh measured 80f breakdown (PROPAINTER_TIME_STAGES=1): GPU compute only ~41% of wall — transformer 2131ms + encoder 1507ms + feat_prop/rest; host I/O 24%; one-time init ~2s. The BENCHMARK number (bench_fork total_inference_s = bench_t0->total) covers ONLY the 4 GPU stages — data_loading is pre-timer (setup), output_write untimed. So host-I/O-overlap is invisible to the bench; only GPU-compute levers move it.
- torch.compile(dynamic=True) on encoder+decoder: steady-state WINS ~13-18% (isolated micro-bench), 0 recompiles. BUT fixed ~1.8s first-window Dynamo-trace tax per fresh process => net LOSS for single-video (13.75->15.77s). Warm TORCHINDUCTOR_CACHE_DIR only avoids re-codegen, not the trace. Rejected for shipping.
- AOTInductor: torch.export + aoti_compile_and_package the encoder (b*t,5,H,W) / decoder (b*l_t,128,H/4,W/4) with dynamic dim0; aoti_load_package = ~23ms => banks the fusion win with NO trace tax. Result 720p80: 13.749 -> 13.373s (-376ms, 1.028x), PSNR 43.35 dB vs eager (>40 threshold).
- Files: model/aoti.py (new), inference_propainter.py + bench_fork.py (PROPAINTER_AOTI=1 gate + --compile-targets), scripts/bench/run_benchmark.py (PROPAINTER_AOTI env passthrough), scripts/experiments/{bench_encoder_compile,probe_aoti_encoder,probe_aoti_decoder}.py. weights/aoti/ gitignored (packages built on first use, keyed by shape/dtype).
- **Learnings for future iterations:**
  - At ProPainter's many-small-varying-window inference, ANY torch.compile-family path pays a per-process trace/plan-warmup tax that doesn't amortize over one video (~175-window break-even). This is the SAME root cause that made the fused transformer kernels lose end-to-end. AOTInductor is the escape hatch: ahead-of-time .pt2, ~23ms load, no Dynamo at runtime.
  - torch.export dynamic_shapes named-dict keys must match the module's forward arg name (encoder `x`, decoder `input`). Use the positional tuple form `dynamic_shapes=({0: bt},)` to be arg-name-agnostic.
  - The bench's headline number is the GPU region only; before optimizing, confirm whether a lever lands inside bench_t0->total or in the untimed setup/output. Host-I/O work is NOT in it.
  - dynamic=True is mandatory for the conv stacks: b*t (local + variable ref frames) changes per window; static would recompile every window.
